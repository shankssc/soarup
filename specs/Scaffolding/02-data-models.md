# 02 — Data Models
> **Status:** Living document · **Last updated:** 2025-03 · **References:** 01-architecture.md

## Overview

All data lives in Supabase Postgres. Row-level security (RLS) is enforced at the database layer on every user-facing table. Migrations are managed with Alembic. This document defines the canonical schema — the single source of truth that both the API code and the frontend TypeScript types are generated from.

---

## Entity relationship summary

```
Workspace
  └── has many WorkspaceMembers (users + roles)
  └── has many DigestSettings (schedule, channels)
  └── has many Updates (via user's membership)

User (managed by Supabase Auth)
  └── has one UserProfile (display name, timezone, preferences)
  └── has many WorkspaceMemberships
  └── has many Updates

Update
  └── belongs to User
  └── belongs to Workspace
  └── has one AudioFile (optional, stored in R2)
  └── has one Transcript (optional, generated by Whisper)
  └── has one Summary (generated by Claude)

Digest
  └── belongs to Workspace
  └── has many DigestItems (one per Update included)
  └── delivered via DigestDelivery records
```

## Table definitions

### `user_profiles`
Extends Supabase Auth's `auth.users` table with application-level fields.

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `id` | `uuid` | PK, FK → `auth.users.id` | Matches Supabase Auth user ID |
| `display_name` | `text` | NOT NULL | Shown in digests and UI |
| `avatar_url` | `text` | nullable | Optional profile image URL |
| `timezone` | `text` | NOT NULL, default `UTC` | IANA timezone string |
| `default_update_mode` | `text` | NOT NULL, default `text` | `text` or `voice` |
| `onboarded_at` | `timestamptz` | nullable | NULL until onboarding complete |
| `created_at` | `timestamptz` | NOT NULL, default `now()` | |
| `updated_at` | `timestamptz` | NOT NULL, default `now()` | Auto-updated via trigger |

**RLS:** Users can read and update only their own row.

### `updates`
The core entity — one standup update per user per day (soft-enforced).

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `id` | `uuid` | PK, default `gen_random_uuid()` | |
| `workspace_id` | `uuid` | NOT NULL, FK → `workspaces.id` | |
| `user_id` | `uuid` | NOT NULL, FK → `auth.users.id` | |
| `input_mode` | `text` | NOT NULL | `text` or `voice` |
| `raw_text` | `text` | nullable | Present if `input_mode = text` |
| `audio_r2_key` | `text` | nullable | R2 object key if `input_mode = voice` |
| `audio_duration_seconds` | `integer` | nullable | Duration of audio file |
| `transcript` | `text` | nullable | Whisper output |
| `summary` | `text` | nullable | Claude output |
| `status` | `text` | NOT NULL, default `pending` | `pending`, `processing`, `processed`, `failed` |
| `submitted_date` | `date` | NOT NULL | Business date of the update (user's timezone) |
| `blockers` | `text[]` | nullable | Extracted blocker items (future: AI-extracted) |
| `created_at` | `timestamptz` | NOT NULL, default `now()` | |
| `updated_at` | `timestamptz` | NOT NULL, default `now()` | |

**RLS:** Members of the workspace can read updates. Users can only create/update/delete their own updates.

**Index:** `(workspace_id, submitted_date DESC)` for digest queries.

## Migrations strategy

- Managed with **Alembic** (Python).
- Every migration is a forward-only script. No destructive changes without a data migration plan.
- Migration files are committed to `apps/api/alembic/versions/`.
- `make migrate` runs pending migrations against the local Docker Postgres.
- Staging and production migrations run automatically in the Railway deploy pipeline before the new API version starts.
- Schema changes to `auth.*` tables are made only through Supabase dashboard migrations, never through Alembic.

## TypeScript type generation

Frontend types are auto-generated from the Supabase schema using the Supabase CLI:

```bash
supabase gen types typescript --project-id <id> > apps/web/src/lib/types/database.ts
```

This runs as part of the CI pipeline when the schema changes. Types are committed to the repo — the frontend never infers types manually from API responses.
